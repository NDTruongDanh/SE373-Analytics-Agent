## **1\. Use Case Description (UC-02)**

* **Objective:** Enable the Analytics Agent to accurately translate business terminology (e.g., *"net revenue"*, *"net sales"*, *"active customers"*, *"successful orders"*) into valid schema elements, canonical join paths, and business formulas before generating SQL, or answer definitional questions directly.  
* **Primary Knowledge Area:** **K3 (RAG — Retrieval-Augmented Generation)**  
* **Core Capabilities:**  
  1. **Business-to-Schema Grounding:** Resolves non-schema business terms and synonyms (`aliases`) into authoritative formulas, status filters (e.g., `orders.status = 'delivered'`), and safe join rules (preventing fan-out duplicate counting when joining `orders` with `order_items` or `payments`).  
  2. **Direct Definitional Q\&A:** Answers questions like *"How is an active customer calculated?"* directly from retrieved knowledge chunks without running unnecessary SQL queries.  
  3. **Unknown-Term Guardrail:** When a user asks about an undefined metric (e.g., *"What is our NPS score?"*), the agent explicitly states that the metric is not in the data dictionary and asks the user for clarification instead of inventing a formula.  
  4. **Verified Citations:** Every SQL query and answer cites the exact knowledge identifiers (`metric_id` or `table.column`) used, verified by a deterministic validator (100% citation validity).  
  5. **Incremental Re-indexing (Delta Updates):** Modifying a metric definition in the knowledge base and running the indexer re-embeds **only** the modified chunk via content-hash comparison, immediately updating subsequent agent responses.

## **2\. Features & Technical Implementation (`TS + LangGraph + pgvector + BM25`)**

### **Feature 1: Semantic Knowledge Base Corpus (`semantic/`)**

Since your team has not finalized the dataset yet, structure the knowledge base as modular YAML/JSON files under `semantic/` (using the recommended localized **Olist E-Commerce** dataset as the default schema: `customers`, `orders`, `order_items`, `products`, `categories`, `sellers`, `payments`, `reviews`, `regions`, `channels`, `employees`, `promotions`).

Organize the corpus into **5 semantic document types** (`doc_type`):

1. **`table` chunks (`semantic/tables.yaml`):** 1 chunk per table (8–15 tables) describing business purpose, primary keys, grain (e.g., 1 row per order), and row count scale.  
2. **`column` chunks (`semantic/columns.yaml`):** 1 chunk per important/tricky column with data type, sample values, enum meanings (e.g., `orders.status` ∈ `['delivered', 'shipped', 'canceled', 'returned']` where `'canceled'` orders are excluded from revenue), and `sensitivity` (`public` \| `internal` \| `restricted_pii` for `customers.phone`, `customers.email`, `customers.address`, `employees.salary`).  
3. **`metric` chunks (`semantic/metrics.yaml` — minimum 10–12 metrics):**  
   * Required metrics to include:  
     1. `metric:net_revenue` (*Doanh thu thuần* — aliases: `["net sales", "doanh số ròng", "doanh thu thực"]`)  
     2. `metric:gross_merchandise_value` (*GMV / Tổng giá trị hàng hoá*)  
     3. `metric:active_customers` (*Khách hàng hoạt động* — ≥1 delivered order in last 90 days)  
     4. `metric:aov` (*Giá trị đơn hàng trung bình / Average Order Value*)  
     5. `metric:return_rate` (*Tỉ lệ hoàn đơn*)  
     6. `metric:cancellation_rate` (*Tỉ lệ huỷ đơn*)  
     7. `metric:repeat_customer_rate` (*Tỉ lệ khách quay lại*)  
     8. `metric:new_customers` (*Khách hàng mới*)  
     9. `metric:on_time_delivery_rate` (*Tỉ lệ giao hàng đúng hạn*)  
     10. `metric:revenue_per_seller` (*Doanh thu trung bình mỗi nhà bán*)  
4. **`join_rule` chunks (`semantic/joins.yaml`):** Canonical join paths and explicit anti-fanout patterns (e.g., *"Warning: `payments` has multiple rows per `order_id` (installments/vouchers). Never `SUM(order_items.price)` directly in a query that joins `orders`, `order_items`, and `payments` without pre-aggregating `payments` in a CTE"*).  
5. **`example` chunks (`semantic/examples.yaml`):** 15–20 few-shot `{question, sql, cited_metrics, tables}` pairs covering time comparisons, CTEs, and multi-table joins (must be **100% disjoint** from the 30+ evaluation questions in `evals/questions/`).

### **Feature 2: Semantic-Unit Chunker & Incremental Indexer (`src/semantic/indexer.ts`)**

Instead of fixed-token sliding windows (which split SQL formulas away from their metric names), chunk **by semantic unit** (1 YAML entry \= 1 self-contained chunk) and store them in PostgreSQL with `pgvector`.

#### **Incremental Re-indexing Algorithm (Acceptance Criterion \#5)**

1. Parse `semantic/*.yaml` into `SemanticChunkInput[]` objects and compute `sha256(canonicalJson(chunk))`.  
2. Query `SELECT chunk_id, content_hash FROM semantic_chunks`.  
3. Diff into three sets:  
   * `unchanged`: `db.content_hash === local.content_hash` → **Skip embedding API call**.  
   * `toUpsert`: new or modified chunks → Batch embed only these chunks and `INSERT ... ON CONFLICT (chunk_id) DO UPDATE`.  
   * `toDelete`: chunks removed from YAML → `DELETE FROM semantic_chunks WHERE chunk_id = ANY($1)`.  
4. Rebuild the in-memory BM25 index on startup or after an incremental update (`indexer.refreshBm25Index()`).  
5. Return an indexing summary `{ added, updated, skipped, deleted, durationMs }` so your logs/demo clearly prove that editing 1 metric only re-indexed 1 chunk (`updated: 1, skipped: N-1`).

### **Feature 4: Unknown-Term Guardrail & Direct Definitional Q\&A (`src/agent/nodes/semanticNode.ts`)**

Add a structured pre-check node in LangGraph right after intent extraction

* **How Unknown-Term Detection Works (Acceptance Criterion \#4):**  
  * During the `understand` step, extract candidate metric/business terms (`extractedBusinessTerms`, e.g., `["NPS"]` or `["Customer Acquisition Cost"]`).  
  * For each requested metric term, check if the top retrieved `metric` or `column` chunk has either:  
    * `aliasMatched === true`, OR  
    * `denseScore >= 0.62` (calibrated threshold on validation set) AND the LLM relevance verifier confirms the chunk defines that term.  
  * If a requested metric is **unmatched**, route immediately to `status: "cannot_answer"` with a polite clarification prompt listing the closest available metrics in the dictionary (never hallucinating a SQL formula).  
* **How Direct Definition Lookup Works:**  
  * If the user asks *"How is X calculated?"* or *"What does Y mean?"* (`queryMode === "definition_lookup"`), bypass `generate_sql` and synthesize the explanation directly from the retrieved `metric` / `column` chunk, including its formula, SQL snippet, caveats, and verified `citations`.

### **Feature 5: Deterministic Citation Validator (`src/semantic/citationValidator.ts`)**

Extend the shared `SQLAnswer` output schema (used with UC-01) with structured `citations`

**Validation Rules (Acceptance Criterion \#3 — 100% Valid Citations):**

1. Query the cached catalog of valid `chunk_id`s and `table.column` identifiers from PostgreSQL.  
2. Verify that **every** `citation.id` in the agent's output exists in the catalog AND was present in the retrieved context for the current turn.  
3. If the query uses a defined business metric, verify that at least one `metric:*` citation is included.  
4. If validation fails, return a structured error to the LangGraph self-correction loop (up to 2 retries) instructing the model to replace invalid IDs with exact IDs from the provided context.
