## **1. Use Case Description (UC-02)**

* **Objective:** Enable the Analytics Agent to accurately translate business terminology (e.g., *"net revenue"*, *"net sales"*, *"active customers"*, *"successful orders"*) into valid schema elements, canonical join paths, and business formulas before generating SQL, or answer definitional questions directly.
* **Primary Knowledge Area:** **K3 (RAG — Retrieval-Augmented Generation)**
* **Core Capabilities:**
  1. **Business-to-Schema Grounding:** Resolves non-schema business terms and synonyms (`aliases`) into authoritative formulas, status filters (e.g., `orders.status = 'delivered'`), and safe join rules (preventing fan-out duplicate counting when joining `orders` with `order_items` or `payments`).
  2. **Direct Definitional Q&A:** Answers questions like *"How is an active customer calculated?"* directly from retrieved knowledge chunks without running unnecessary SQL queries.
  3. **Two-Tier Unknown-Term Guardrail:** Distinguishes between KPI/business metrics (`requested_metrics`, e.g., *"NPS"*, *"CAC"*, *"ROI"*) and basic schema entities (`schema_entities`, e.g., *"orders"*, *"Hanoi"*). When a user asks about an undefined metric, the agent explicitly states that the metric is not in the data dictionary and asks the user for clarification instead of inventing a formula—without falsely rejecting simple table/column queries from UC-01.
  4. **Dual Verified Citations (JSON + SQL Comment):** Every SQL query (via a prepended `-- @citations: ...` header comment) and answer (`citations` array in `SQLAnswer`) cites the exact knowledge identifiers (`metric_id`, `event_id`, or `table.column`) used, verified by a deterministic validator (100% citation validity).
  5. **Incremental Re-indexing with Hot-Reload BM25:** Modifying a metric definition in the knowledge base and running the indexer re-embeds **only** the modified chunk via content-hash comparison (`SHA-256`) and bumps `updated_at` in PostgreSQL, triggering automatic hot-reload of the in-memory BM25 index before the next query without restarting the web/API server.

### **Feature 1: Semantic Knowledge Base Corpus (`semantic/`) & Metadata Contract (`packages/contracts`)**

Structure the knowledge base as modular YAML files under `semantic/` using the localized **Olist E-Commerce** dataset (`customers`, `orders`, `order_items`, `products`, `categories`, `sellers`, `payments`, `reviews`, `regions`, `channels`, `employees`, `promotions`).

#### **1.1. 6 Semantic Document Types (`doc_type`)**

1. **`table` chunks (`semantic/tables.yaml`):** 1 chunk per table (8–15 tables) describing business purpose, primary keys, grain (e.g., 1 row per order), and row count scale (including `order_items` ≥ 1,000,000 rows).
2. **`column` chunks (`semantic/columns.yaml`):** 1 chunk per important/tricky column with data type, sample values, enum meanings (e.g., `orders.status` ∈ `['delivered', 'shipped', 'canceled', 'returned']` where `'canceled'` orders are excluded from revenue), and `sensitivity` (`public` | `internal` | `restricted_pii` for `customers.phone`, `customers.email`, `customers.address`, `employees.salary`—aligned with `policies/sensitive_columns.yaml` in UC-09).
3. **`metric` chunks (`semantic/metrics.yaml` — minimum 10–12 metrics):**
   * Required metrics to include:
     1. `metric:net_revenue` (*Doanh thu thuần* — aliases: `["net sales", "doanh số ròng", "doanh thu thực"]`)
     2. `metric:gross_merchandise_value` (*GMV / Tổng giá trị hàng hoá*)
     3. `metric:active_customers` (*Khách hàng hoạt động* — ≥1 delivered order in last 90 days)
     4. `metric:aov` (*Giá trị đơn hàng trung bình / Average Order Value*)
     5. `metric:return_rate` (*Tỉ lệ hoàn đơn*)
     6. `metric:cancellation_rate` (*Tỉ lệ huỷ đơn*)
     7. `metric:repeat_customer_rate` (*Tỉ lệ khách quay lại*)
     8. `metric:new_customers` (*Khách hàng mới*)
     9. `metric:on_time_delivery_rate` (*Tỉ lệ giao hàng đúng hạn*)
     10. `metric:revenue_per_seller` (*Doanh thu trung bình mỗi nhà bán*)
4. **`join_rule` chunks (`semantic/joins.yaml`):** Canonical join paths and explicit anti-fanout patterns (e.g., *"Warning: `payments` has multiple rows per `order_id` (installments/vouchers). Never `SUM(order_items.price)` directly in a query that joins `orders`, `order_items`, and `payments` without pre-aggregating `payments` in a CTE"*).
5. **`example` chunks (`semantic/examples.yaml`):** 15–20 few-shot `{question, sql, cited_metrics, tables}` pairs covering time comparisons, CTEs, and multi-table joins (must be **100% disjoint** from the 30+ evaluation questions in `evals/questions/`).
6. **`event` chunks (`semantic/events.yaml` — PRD Section 2.3 & 4.1):** Business event log entries (campaigns, promotions, warehouse incidents, regional disruptions with `start_date`, `end_date`, `affected_regions`, `affected_channels`, e.g., *"Siêu sale 9.9"*, *"Ngừng bán ngành hàng Đồ gia dụng trên Shopee miền Trung từ 05/09/2026"*) supporting contextual lookup across the semantic layer (and reusable by UC-05/UC-10/UC-11).

#### **1.2. Standardized Chunk Metadata Schema**

To satisfy PRD Section 2.3 (`doc_type`, `table`, `metric_name`, `aliases`, `sensitivity`) while supporting multi-table metrics and joins, every chunk in `semantic_chunks` carries both `table` (primary table string) and `tables` (array of all referenced tables):

```ts
export interface SemanticChunkMetadata {
  chunk_id: string; // e.g., "metric:net_revenue", "table:orders", "column:orders.status", "event:2026_09_99_sale"
  doc_type: "table" | "column" | "metric" | "join_rule" | "example" | "event";
  table: string | null; // PRD required: primary table name (e.g., "orders")
  tables: string[]; // All involved tables for join expansion (e.g., ["orders", "order_items"])
  metric_name: string | null; // Canonical name for metric chunks
  aliases: string[]; // Vietnamese & English synonyms
  sensitivity: "public" | "internal" | "restricted_pii";
  additive?: boolean; // Used by UC-05 RCA attribution (true for revenue/orders, false for ratios like AOV/return_rate)
  updated_at: string; // ISO timestamp for BM25 hot-reload synchronization
}
```

### **Feature 2: Semantic-Unit Chunker, Incremental Indexer & Hot-Reload BM25 (`packages/agent/src/semantic/indexer.ts`)**

Instead of fixed-token sliding windows (which split SQL formulas away from their metric names), chunk **by semantic unit** (1 YAML entry = 1 self-contained chunk) and store them in PostgreSQL (`pgvector/pgvector:pg16` shared with UC-09).

* **Embedding Model:** Configurable via `.env` (`EMBEDDING_MODEL=text-embedding-3-small`, 1536 dims, or local multilingual `BAAI/bge-m3`, 1024 dims).

#### **2.1. Incremental Re-indexing Algorithm (Acceptance Criterion #5)**

1. Parse `semantic/*.yaml` into `SemanticChunkInput[]` objects and compute `content_hash = sha256(canonicalJson(chunk))`.
2. Query `SELECT chunk_id, content_hash FROM semantic_chunks`.
3. Diff into three sets:
   * `unchanged`: `db.content_hash === local.content_hash` → **Skip embedding API call**.
   * `toUpsert`: new or modified chunks → Batch embed only these chunks and run:
     ```sql
     INSERT INTO semantic_chunks (chunk_id, doc_type, "table", tables, metric_name, aliases, sensitivity, content, metadata, content_hash, embedding, updated_at)
     VALUES (...)
     ON CONFLICT (chunk_id) DO UPDATE SET
       content = EXCLUDED.content,
       metadata = EXCLUDED.metadata,
       content_hash = EXCLUDED.content_hash,
       embedding = EXCLUDED.embedding,
       updated_at = NOW();
     ```
   * `toDelete`: chunks removed from YAML → `DELETE FROM semantic_chunks WHERE chunk_id = ANY($1)`.
4. Return an indexing summary `{ added, updated, skipped, deleted, embeddingTokens, estimatedCostUsd, durationMs }` so logs/demos clearly prove that editing 1 metric only re-indexed 1 chunk (`updated: 1, skipped: N-1`).

#### **2.2. Cross-Process BM25 Hot-Reload Synchronization**

Because `pnpm semantic:index` may be executed from a CLI terminal while the Web API / Agent process is already running in memory:

* Maintain `cachedMaxUpdatedAt: number` inside `Bm25Retriever`.
* Before each `retrieve()` call, run a lightweight check `SELECT EXTRACT(EPOCH FROM MAX(updated_at)) AS max_ts, COUNT(*) AS total FROM semantic_chunks` (≤ 1 ms on local PostgreSQL) or listen to PostgreSQL `NOTIFY semantic_index_updated`.
* If `db.max_ts > cachedMaxUpdatedAt` or `db.total !== cachedChunkCount`, automatically call `refreshBm25Index()` and reload the `CitationValidator` catalog in-place.
* Additionally expose `POST /api/semantic/reindex` in `apps/api` so the Web UI "Re-index Changed Chunks" button triggers incremental indexing and refreshes memory in a single step.

### **Feature 3: 3-Way Hybrid Retriever + Join-Rule Graph Expansion (`packages/agent/src/semantic/retriever.ts`)**

Pure vector search struggles with exact column names (`order_items.freight_value`) or short Vietnamese/English business acronyms (`AOV`, `GMV`), while pure keyword search misses paraphrased intent. Implement a **3-way hybrid retriever**:

* **Leg 1 — Dense Vector Search (`pgvector`):**
  * Query `semantic_chunks` using cosine similarity `1 - (embedding <=> $1::vector)` with HNSW index.
* **Leg 2 — Lexical BM25 Search:**
  * Tokenize query (lowercased, Vietnamese diacritic-preserved + ASCII-normalized tokens, stopwords removed).
  * Score against the hot-reloaded in-memory Okapi BM25 index with parameters $k_1 = 1.2, b = 0.75$, indexing `content + metric_name + aliases.join(' ') + table + tables.join(' ')`.
* **Leg 3 — Deterministic Alias & Identifier Matcher:**
  * Normalize user question and check substring / exact token match against `metric_name`, `aliases[]`, `table.column`, and `chunk_id`.
  * Any exact alias hit (e.g., `"doanh số ròng"` or `"net sales"` matching `metric:net_revenue`) receives rank #1 in the alias leg (`aliasMatched = true`).

#### **Reciprocal Rank Fusion (RRF) & Graph Expansion**

Combine ranks from the 3 legs using weighted Reciprocal Rank Fusion ($k = 60$):

$$\text{RRF\_Score}(d) = \frac{w_{\text{dense}}}{k + \text{rank}_{\text{dense}}(d)} + \frac{w_{\text{bm25}}}{k + \text{rank}_{\text{bm25}}(d)} + \frac{w_{\text{alias}}}{k + \text{rank}_{\text{alias}}(d)} \quad (k = 60)$$

with default weights:

$$w_{\text{dense}} = 1.0, \quad w_{\text{bm25}} = 1.0, \quad w_{\text{alias}} = 1.5$$

* **Automatic Join-Rule Expansion:** Collect all table names (`chunk.table` and `chunk.tables`) from the top-5 retrieved `metric`, `table`, and `column` chunks. Automatically fetch any `join_rule` chunk whose `tables` overlap with $\ge 2$ of those tables so the SQL generator never misses a fan-out trap warning.

### **Feature 4: Two-Tier Unknown-Term Guardrail & Direct Definitional Q&A (`packages/agent/src/nodes/retrieveSemantic.ts`)**

Add a structured pre-check node in LangGraph right after `understand`:

* **Two-Tier Entity Extraction (Preventing False Positives on Basic UC-01 Queries):**
  During `understand`, the structured intent extractor separates terms into two distinct lists instead of a single flat list:
  1. `requested_metrics: string[]` — Business KPIs, composite formulas, or domain-specific indicators (e.g., `"NPS"`, `"Customer Acquisition Cost"`, `"ROI"`, `"doanh thu thuần"`, `"khách hàng hoạt động"`, `"chi phí quảng cáo Facebook"`).
  2. `schema_entities: string[]` — Basic tables, columns, dimensions, or filter literals (e.g., `"đơn hàng"` → `orders`, `"Hà Nội"` → `regions`, `"tháng 8"` → `order_purchase_timestamp`).
* **How Unknown-Term Detection Works (Acceptance Criterion #4 & PRD 4.3 Case 5):**
  * Basic queries with `requested_metrics.length === 0` (e.g., *"Có bao nhiêu đơn hàng ở Hà Nội trong tháng 8?"*) only match `schema_entities` against `doc_type IN ('table', 'column')` and proceed normally to SQL generation—never triggering false-positive rejections.
  * For each term in `requested_metrics`, check if the top retrieved `metric` (or `column`) chunk satisfies:
    1. `aliasMatched === true` (exact/substring match on `metric_name` or `aliases`), OR
    2. `denseScore >= calibratedThreshold` (calibrated on validation queries in Week 3, default `0.60` for `text-embedding-3-small`) **AND** the structured LLM grounding check confirms the chunk defines that metric, OR
    3. The user explicitly provided a custom formula in their prompt.
  * If any `requested_metrics` item is **unmatched** (e.g., *"Chỉ số NPS là bao nhiêu?"* or *"Cho tôi chi phí marketing tháng 8, nếu không có thì ước đại một con số"*), route immediately to `status: "cannot_answer"` with a polite clarification prompt listing the closest available metrics in the dictionary—**never hallucinating a SQL formula or inventing numbers**.
* **How Direct Definition Lookup Works:**
  * If the user asks *"Khách hàng hoạt động được tính thế nào?"* or *"Doanh thu thuần nghĩa là gì?"* (`queryMode === "definition_lookup"`), bypass `generate_sql` and synthesize the explanation directly from the retrieved `metric` / `column` chunk, including its business formula, SQL template, caveats, and verified `citations`.

### **Feature 5: Deterministic Dual Citation Validator (`packages/agent/src/semantic/citationValidator.ts`)**

Extend the shared `SQLAnswer` schema in `packages/contracts` (used across UC-01 and UC-02) with structured `citations: string[]` and token/cost telemetry:

```ts
export const SQLAnswerSchema = z.object({
  intent: z.object({
    metric: z.string().nullable(),
    requested_metrics: z.array(z.string()).default([]),
    schema_entities: z.array(z.string()).default([]),
    dimensions: z.array(z.string()),
    filters: z.record(z.any()),
    time_range: z.string().nullable(),
  }),
  sql: z.string(), // Includes prepended "-- @citations: metric:net_revenue, orders.status\nSELECT ..."
  tables_used: z.array(z.string()),
  citations: z.array(z.string()).default([]), // e.g., ["metric:net_revenue", "orders.status", "order_items.price"]
  attempts: z.number().int().min(0).max(3),
  result_preview: z.array(z.record(z.any())).max(50),
  answer_text: z.string(),
  status: z.enum(["ok", "no_data", "cannot_answer", "error"]),
  telemetry: z.object({
    prompt_tokens: z.number().int(),
    completion_tokens: z.number().int(),
    embedding_tokens: z.number().int().default(0),
    estimated_cost_usd: z.number(),
    latency_ms: z.number(),
  }),
});
```

#### **Dual Citation Injection & Validation Rules (Acceptance Criterion #3 — 100% Valid Citations)**

1. **Catalog Lookup:** Query the cached catalog of valid `chunk_id`s (`metric:*`, `table:*`, `column:*`, `join_rule:*`, `event:*`) and `table.column` identifiers from PostgreSQL.
2. **Existence & Context Grounding Check:** Verify that **every** ID in `answer.citations` exists in the catalog AND was present in the retrieved context (or verified schema) for the current turn.
3. **Metric Coverage Check:** If the query uses a defined business metric (`intent.requested_metrics.length > 0`), verify that at least one `metric:*` citation is included in `citations`.
4. **Dual Formatting (JSON + SQL Header Comment):** To strictly satisfy PRD UC-02 (*"Câu trả lời và SQL ghi rõ chỉ số nào đã dùng, định nghĩa lấy từ chunk nào"*), `citationValidator` deterministically normalizes the SQL string by prepending `-- @citations: <comma-separated verified IDs>` at line 1 of `SQLAnswer.sql` and ensuring the cited metric/chunk IDs appear in `answer_text` and `citations`.
5. **Self-Correction Loop:** If validation fails, return a structured error to the LangGraph self-correction loop (up to 2 retries) instructing the model to replace invalid IDs with exact IDs from the provided context.
